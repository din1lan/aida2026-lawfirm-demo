# PDF 轉錄修正（分支 `fix/pdf-cjk`，2026-11-04；同日加做瀏覽器內 OCR）

> **2026-11-05 更新**：pdf.js、Tesseract（含繁中語言檔）、xlsx、Tailwind 已全部放進網站的 `vendor/`，不再從 CDN 下載；本文提到 cdnjs、jsDelivr、`CDN_DIR`、「暖機」的地方是舊版說明。測試現在一律在斷網模式下跑（`tests/offline.js`）。詳見 `docs/正式版規格-1105.md`。

## 一句話結論
這次修了兩件事：
1. **中文字型對照表（CMap）**：見下方。
2. **掃描檔 OCR（文字辨識）**：使用者確認回報的那份 5 頁判決是掃描檔（整份是圖片、沒有文字層）。現在遇到圖片頁，會**在使用者自己的瀏覽器裡**用 Tesseract.js（繁體中文）辨識，圖片不送到任何伺服器。辨識完的文字照原流程走（去識別化 → Gemini 或示意版）。詳見「OCR」一節。

**CMap 的部分：**
網站讀 PDF 時沒有告訴 pdf.js「中文字型對照表」放在哪裡。遇到台灣法院常見、**沒有內嵌**的中文字型（細明體、標楷體這類），pdf.js 不知道每個字碼對應哪個中文字，**整份中文全部被丟掉**，還被誤判成「掃描檔」。補上對照表位置後，測試文件 100% 讀到。

## 原因（白話）
- PDF 裡的中文常常不是直接存「字」，而是存「字碼」，要查一張對照表（CMap）才知道是哪個字。
- 字型有內嵌、又附對照表的 PDF（例如 Word、瀏覽器列印出來的）→ 原本就讀得到。
- 字型沒內嵌、靠標準對照表的 PDF（法院、公文系統常見）→ pdf.js 要去下載標準對照表；原本沒給下載位置，pdf.js 直接放棄這個字型，該字型的字全部消失。
- 瀏覽器主控台會出現：`The CMap "baseUrl" parameter must be specified`。

其他懷疑點也查過：
| 懷疑點 | 結果 |
|---|---|
| 片段串接（`str + hasEOL`）吃字或亂序 | 不會吃字。但有些 PDF 換行時不帶換行記號，前後兩行會黏在一起 → 新寫法看到「位置往下移」就補換行（原有 7 份示範 PDF 輸出逐字不變） |
| 頁數或字數上限截斷 | 兩處讀取都沒有上限；25 頁、一萬多字完整讀到 |
| AI 閱卷送 Gemini 前截斷 | 沒有截斷（整份逐頁組好直接送） |
| 掃描頁／圖片頁 | 原本默默跳過，使用者不知道少了哪頁 → 現在畫面紅字寫「第 N 頁是圖片、讀不到文字」 |

## 要注意的地方
- 讀這類字型時，瀏覽器會多從 cdnjs 下載一兩個小檔（對照表，各幾 KB～幾十 KB）。沒網路時 pdf.js 本來就載不進來，情況跟以前一樣。
- 掃描檔第一次辨識會從 cdn.jsdelivr.net 下載約 3MB；比賽現場若網路很慢，建議 demo 前先上傳一次掃描檔「暖機」，讓瀏覽器先快取。
- 「圖片頁」判斷：一頁少於 5 個字而且有畫圖片才算。完全空白的頁不會提示。

## OCR（掃描檔文字辨識）

### 怎麼運作
- 讀 PDF 時，一頁少於 5 個字、而且畫了圖片，就判斷是掃描頁。
- 這時才去下載辨識元件（平常讀一般 PDF **完全不會下載**），把那一頁畫成圖（寬約 2200 像素），在瀏覽器背景執行緒裡辨識。
- AI 自動填、AI 閱卷用同一個函式（`modules/pdftext.js` 的 `read`）。
- 畫面：辨識時顯示「文字辨識中（OCR）：掃描頁 2／5（第 2 頁）｜在你的瀏覽器裡辨識，圖片不會上傳」；完成後橘字標示「第 1、2、3、4、5 頁為 OCR 辨識，可能有錯字，請核對原文」。AI 閱卷文字框該頁開頭也有同樣提醒；AI 自動填按「讓 AI 讀」後提醒仍保留。
- 點「原文」跳回 PDF 時，掃描頁沒辦法在圖上畫黃底（圖上沒有文字位置），會改寫「這一頁是掃描檔，文字由 OCR 辨識（可能有錯字），請對照下方原圖人工核對」。
- 辨識後的清理：拿掉中文字之間的多餘空白、半形標點轉全形（數字裡的逗點保留）、「○○」被認成「00」時換回、去掉掃描雜點變成的孤立符號。

`tesseract.min.js`、`worker.min.js`、`tesseract-core-simd-lstm.wasm.js`、`chi_tra.traineddata.gz`（全部從 cdn.jsdelivr.net，版本釘死）。

### 離線（或 jsDelivr 被擋）時會怎樣
用 `OFFLINE_OCR=1` 模擬，實測：
- 有文字層的頁照常讀。
- 部分頁是圖片：紅字「第 2 頁是圖片、讀不到文字，這幾頁的內容不會送去分析（文字辨識元件載入失敗（需要網路））」。
- 整份是掃描檔：AI 閱卷寫「讀不到文字，可能是掃描檔；文字辨識沒有成功：文字辨識元件載入失敗（需要網路）」＋「請確認網路連線後重新選擇檔案，或改用貼入文字」；AI 自動填寫「讀取失敗：這份 PDF 讀不到文字（可能是掃描檔），文字辨識也沒有成功…請改拍照上傳並用 Gemini，或手動輸入」。
- 不會卡住、不會跳錯誤視窗。

### 示意版的已知限制（不是 OCR 的問題）
示意版（不用金鑰的規則引擎）只認得「113年3月1日」這種阿拉伯數字日期和「第184條」這種法條寫法。虛構判決用中文數字（一一三年、第一百八十四條），所以不管是文字層版還是 OCR 版，示意版都抓不到日期和法條；OCR 版另外偶爾因為雜點認不出當事人。正式的 Gemini 不受這個限制。


## OCR 品質改善（分支 `fix/ocr-quality`，從 main `83dd0a4` 開；尚未合併）

使用者用真實掃描判決實測線上版後回報三個問題：中文字之間被插入很多空白、一句話被切成很多短行還夾空行、截圖和印章被認成一整行亂碼；另外去識別化漏遮「上　訴　人　○○○」這種字間有空白的姓名。全部仍在瀏覽器本機處理，不送任何圖片出去。

### 改了什麼
| 項目 | 做法 |
|---|---|
| 辨識前處理 | pdf.js 以 3 倍算圖 → 灰階時取 RGB 最亮值（紅色印章、彩色對話框變淡）→ Otsu 自動門檻二值化 → 去孤立雜點（`preprocess`） |
| 字距空白 | Tesseract 會在每個中文字之間放空白，一律拿掉；原本「依位置補全形空格」的做法正是使用者看到「主　張　兩　造」的原因，已移除 |
| 斷行 | 同一段的行接回去；遇到「一、」「（一）」「主文」「理由」「事實及理由」「中華民國」「法官」等段落開頭、短的當事人行、上一行明顯較短（段落最後一行）或以「：」結尾才換段；不再有空行（`joinLines`） |
| 亂碼行 | 整行信心 < 20 且中文比例不高或字很少、中文比例 < 5 成且信心 < 60、只剩 1～2 字且信心 < 50 → 丟掉，並在畫面寫「第 N 頁有 K 行無法辨識，已略過」（`isJunkLine`） |
| 行頭行尾雜點 | 行頭的 “ ” - . 等、行尾黏在中文後的 1～3 個英文字母或單一數字（「如下1」「（虛構）ee」）拿掉；「第2」「第六六六號」這類不動（`trimEdges`） |
| 低信心標示 | 單字信心 < 70 的字，在 AI 閱卷文字框裡後面加〔?〕；**送給 AI 的版本不加**，避免影響分析與原文比對 |
| 去識別化 | `modules/deidentify.js` 新增 `joinSpacedHan`：比對前把「上　訴　人　王　小　明」這種被拉開的單字合回「上訴人王小明」；一般句子裡的空白（「李大華 否認」）不動。AI 自動填的 `partyNamesFromText` 也同樣處理 |

### 還剩什麼問題
- 形近字仍會錯（虛→慮、判→列、駁→駿），而且 Tesseract 對很多錯字一樣很有信心。實測三份檔共標了 42 個〔?〕，其中 30 個（71%）真的是錯字；但全部 352 個錯字裡只有 30 個（約 9%）被標到。所以〔?〕只是「提醒這裡特別要看」，**沒標的字不代表正確**，律師仍需對照原圖。
- 壓在印章底下的字、截圖旁邊的字偶爾被一起丟掉或認錯。
- 測試機只有文泉驛正黑字型；真實法院文件是明體／標楷體，數字要用真實文件在正式網路上再量。
- 同一份檔在不同螢幕倍率下結果略有差異：一般倍率略過 6／6／5 行，高解析螢幕（截圖用 2 倍）只略過 2／3／2 行、文字也較乾淨。原因待查（可能是 pdf.js 算圖時跟著螢幕倍率），不影響正確率門檻測試。

## 掃描頁「原文」螢光標示（分支 `feature/ocr-highlight`，疊在 `fix/ocr-cleanup` 上）

以前掃描頁點「原文」只會說「沒辦法在圖上標出位置」。現在：
- 本機 OCR 辨識時，順便把每個字在圖上的位置記下來（只存在瀏覽器記憶體，不上傳、不存檔）。
- 點「原文」時，用模糊比對（容許錯字、漏字、空白、行號已清掉、○○被認成 00）在該頁找最接近原句的一段，換算到畫面位置畫黃框，並寫出相似度；相似度低於 60% 才退回原本的提示。
- 用 Gemini 辨識的頁：Gemini 不給位置，所以背景再用本機 OCR 跑一次「只取位置、不用它的文字」（圖片不上傳）；還沒跑完時先顯示「正在取得位置…」，跑完自動補上黃框。AI 自動填不需要，所以不跑。

實測（`tests/ocr-highlight.e2e.js`，原句取自產生測試檔時真的畫上去的文字，不是 OCR 結果；檢查黃框是否落在該句實際所在的行與位置）：
| 情況 | 標對 |
|---|---|
| 本機 OCR，S1 乾淨掃描 | 12／12 |
| 本機 OCR，S2 模擬掃描 | 11／12 |
| Gemini 辨識＋背景本機座標，S1 | 12／12 |

唯一標錯的一句：該頁有兩行幾乎一樣（只差當事人代號一個字），OCR 又把那個字認錯，黃框落到隔壁那行。截圖：`docs/screenshots/ocr-highlight/`。

## 建議（之後可以做）
- 用真實（去識別化後）的法院掃描檔，在正式網路上量一次正確率與速度。
- 頁數很多的掃描檔（例如 50 頁）要 3～4 分鐘，可以考慮加「停止辨識」按鈕，或只辨識使用者選的頁。
- 若想完全不依賴外部 CDN，可把 Tesseract 檔案放到自己的網站上（約 5.8MB）。
